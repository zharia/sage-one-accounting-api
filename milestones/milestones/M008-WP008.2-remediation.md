# M008 — WP008.2 Remediation and Release-Pipeline Recovery

**Project:** Sage One Accounting API — TypeScript SDK  
**Repository:** `zharia/sage-one-accounting-api`  
**Parent milestone:** M008 — Quality and Production Assurance  
**Work package:** WP008.2R — Scheduler hardening and release recovery  
**Priority:** Critical  
**Status:** Ready for development  
**Predecessors:** WP008.1 and WP008.2 implementation  
**Purpose:** Resolve the review findings against the central request scheduler and restore a demonstrably reliable, controlled release workflow.

---

## 1. Executive Summary

The implementation of WP008.2 introduced a central request scheduler in `src/transport/scheduler.ts`, integrated with the existing transport execution path. The architecture is directionally sound and should be retained.

The review identified several remaining issues which prevent unconditional acceptance:

1. The scheduler's default per-company pacing is `minIntervalMs: 0`, which does not implement Sage's published recommendation to avoid exceeding approximately one request per second.
2. HTTP 429 handling needs to distinguish a rate-limit lockout from ordinary transient failures. A generic exponential-backoff retry must not continue generating requests during a server-imposed block.
3. Cancellation during an awaited backoff sleep may escape the SDK's normal error mapping and surface as a generic `Error`, rather than the documented `SageTimeoutError` with `isAborted: true`.
4. Scheduler coordination is local to one `SageTransport` instance. This boundary must be documented and its implications for multiple clients and processes made explicit.
5. The authentication preflight request bypasses the scheduler. Repeated failed authentication attempts therefore need explicit handling and documentation.
6. The GitHub Changesets release workflow currently fails at its release/publish action. The precise failure cause must be established from workflow logs before modifying configuration.

This work package is a targeted remediation. It is not an invitation to redesign the transport architecture, introduce distributed coordination, or broaden SDK scope.

**The existing scheduler and transport abstractions remain authoritative. Fix demonstrated defects at their source, add regression tests, and preserve public API compatibility wherever reasonably possible.**

## 3. WP008.2R.1 — Default Request Pacing

**Priority:** P1  
**Primary area:** `src/transport/scheduler.ts`, client configuration and documentation

### 3.1 Problem

The current scheduler defaults to:

```ts
minIntervalMs: 0
```

This permits consecutive dispatches without a pacing interval. A concurrency cap of four does not itself constrain requests to a safe per-company rate.

### 3.2 Requirements

1. Set the default request pacing interval to **1,000 milliseconds** for each effective Sage throttling identity, reflecting Sage's published recommendation of no more than one request per second. Reconfirm this against the official source before implementation.
2. Preserve explicit user configurability.
3. Ensure the pacing interval applies to dispatches within a company lane, not merely to request completion.
4. Ensure concurrent requests cannot bypass the lane pacing rule.
5. Retain global concurrency control independently of per-company pacing.
6. Ensure one company's pacing or suspension does not block unrelated company lanes, except where verified Sage documentation establishes a shared limit.
7. Document that the scheduler is a client-side safeguard, not a guarantee that every Sage-side throttling condition is prevented.
8. Do not hard-code an undocumented Sage quota as an invariant of the SDK.

### 3.3 Configuration compatibility

Inspect the existing public configuration shape before changing it.

- Prefer changing the default value without introducing a new public option.
- If a new option is required, document its units, default, bounds and precedence.
- Do not silently reinterpret existing configuration values.
- Add tests for default construction and explicit overrides.

### 3.4 Acceptance criteria

- [x] Default per-company pacing is 1,000 ms, unless official documentation review establishes a materially different current recommendation.
- [x] Explicit configuration overrides the default.
- [x] Dispatch pacing is deterministic under a fake clock.
- [x] Multiple concurrent requests in one lane cannot bypass pacing.
- [x] Independent company lanes continue to make progress.
- [x] Documentation distinguishes Sage guidance from SDK policy.
- [x] Existing scheduler and transport tests remain green.

## 4. WP008.2R.2 — HTTP 429 and Rate-Limit Lockout Semantics

**Priority:** P1  
**Primary area:** `src/transport/scheduler.ts`, transport retry policy and error mapping

### 4.1 Problem

HTTP 429 is not merely another transient server failure. Sage may impose a temporary block after a request-rate threshold is exceeded. Continuing to send retries during that period can prolong or aggravate the block.

A generic exponential-backoff fallback is therefore not sufficient unless its behaviour is explicitly reconciled with Sage's current documented policy.

### 4.2 Required behaviour

The implementation must distinguish at least these conditions:

1. **Ordinary transient failure:** for example, a retryable 5xx response.
2. **Rate-limit response:** HTTP 429, with or without a valid `Retry-After` header.
3. **Authentication failure or authentication throttling:** failed login or validation attempts, which must not be treated as an ordinary resource-request 429 without evidence.
4. **Other client errors:** not automatically retried unless an explicit operation policy permits it.

### 4.3 Handling a 429 response

When a normal API request receives HTTP 429:

- Suspend dispatch in the affected scheduler lane.
- Parse `Retry-After` as delta-seconds or HTTP-date when present and valid.
- Do not dispatch another request in that lane before the applicable suspension expires.
- Do not allow retries of the original request to bypass the lane suspension.
- Keep unrelated lanes operational where the documented limit is isolated to the affected company.
- Preserve the original request's correlation and error context.
- Emit structured, redacted diagnostics identifying the rate-limit event and suspension duration.

When `Retry-After` is missing or invalid:

- Do not treat the response as an ordinary 503 and immediately enter an unbounded retry loop.
- Determine the conservative fallback suspension from current official Sage documentation.
- If Sage's documentation does not specify a reliable fallback duration, make the fallback explicit and configurable, document the rationale, and surface the original `SageRateLimitError` to the caller rather than silently retrying indefinitely.
- Do not invent a server guarantee.

The scheduler's maximum accepted `Retry-After` value must not cause the client to resume earlier than the server-directed time. If a configured maximum wait is exceeded, the SDK may fail the request to the caller, but it must not shorten the lane suspension and resume dispatch prematurely.

### 4.4 Retry policy

A 429 response must not be conflated with the generic transient retry policy.

The agent must inspect the existing implementation and make the retry contract explicit:

- Whether the original request is automatically retried after a valid `Retry-After`.
- Whether the default is to return `SageRateLimitError` immediately while suspending the lane.
- How cancellation interacts with a pending rate-limit delay.
- How the request's retry budget and overall timeout interact with the suspension.

The chosen behaviour must be conservative, documented and tested. In particular, the scheduler must never issue repeated requests during a known active block.

Financial mutation safety remains absolute:

- POST, PUT and DELETE must not be automatically replayed merely because a 429 or another transport error occurred.
- An explicit retry opt-in must not override a known ambiguous financial outcome without an established idempotency guarantee.
- Do not assume Sage supports idempotency keys unless verified.

### 4.5 Authentication throttling

The initial `Login/Validate` preflight currently occurs outside the normal request scheduler.

Do not force authentication into the resource scheduler without understanding client construction and token lifecycle.

Instead:

- Inspect the authentication flow and its error mapping.
- Ensure repeated authentication failures are not automatically retried in a tight loop.
- Ensure the original authentication error is preserved.
- Document that preflight authentication is outside the per-company resource scheduler, if that remains the design.
- If the authentication endpoint has a documented independent throttle, represent it explicitly rather than pretending it shares the ordinary resource-request lane.
- Add tests proving that failed authentication does not trigger an uncontrolled retry sequence.

### 4.6 Acceptance criteria

- [x] HTTP 429 is handled distinctly from generic 5xx retry behaviour.
- [x] Valid delta-seconds `Retry-After` suspends the correct lane.
- [x] Valid HTTP-date `Retry-After` suspends the correct lane.
- [x] Missing and invalid `Retry-After` follow the documented conservative policy.
- [x] A configured maximum wait never causes premature lane resumption.
- [x] No request is dispatched in a suspended lane before expiry.
- [x] Unrelated lanes remain operational where isolation is supported by Sage's documented limit scope.
- [x] Authentication failures cannot cause uncontrolled retry loops.
- [x] Mutation requests are not replayed unsafely.
- [x] Tests cover retry budgets, request timeouts, cancellation and suspension interactions.
- [x] Official Sage source and the selected policy are recorded in documentation or an ADR.

## 5. WP008.2R.3 — Cancellation During Backoff

**Priority:** P1  
**Primary area:** transport retry loop, abortable sleep and SDK errors

### 5.1 Problem

The review identified a possible error-normalisation defect when a caller aborts a request while the transport is awaiting a retry backoff delay.

If `abortableSleep()` rejects with a generic `Error`, and that rejection occurs inside an existing catch/retry branch, it may escape the transport's normal abort mapping.

The expected public contract is a `SageTimeoutError` with `isAborted: true`, consistent with other caller-initiated abort paths.

### 5.2 Required correction

Inspect the actual current control flow and reproduce the behaviour before changing code.

The correction must:

- Preserve the original abort signal.
- Ensure abort during a retry delay terminates the retry sequence.
- Ensure no later HTTP request is dispatched.
- Map caller-initiated abort to the SDK's documented abort error type.
- Preserve timeout versus explicit cancellation distinctions where the SDK currently distinguishes them.
- Avoid wrapping or replacing an existing meaningful SDK error unnecessarily.
- Remove abort listeners and timers on both resolution and rejection paths.

Do not merely change the message string. The public error class and discriminating properties must be correct.

### 5.3 Required regression tests

At minimum:

1. A GET request receives a retryable 503.
2. The transport begins its retry delay.
3. The caller aborts during that delay.
4. The returned promise rejects with `SageTimeoutError`.
5. `isAborted` is `true`.
6. The fetch implementation is not invoked again.
7. Timers and abort listeners are cleaned up.

Also test:

- Abort before the delay begins.
- Abort immediately as the delay expires.
- Abort during a rate-limit suspension.
- Request timeout expiring during a backoff delay.
- Repeated abort notification does not settle the request more than once.

Use fake timers or an injected clock. Tests must not rely on arbitrary real-time sleeps.

### 5.4 Acceptance criteria

- [x] Cancellation during backoff produces the documented SDK error.
- [x] No subsequent request is dispatched after cancellation.
- [x] Timeout and caller-abort semantics remain distinguishable where specified.
- [x] Timers and listeners are cleaned up.
- [x] All race-condition tests are deterministic.
- [x] Existing error and transport tests pass.

## 6. WP008.2R.4 — Scheduler Scope and Multi-Client Coordination Boundary

**Priority:** P2  
**Primary area:** scheduler documentation, client configuration and architecture records

### 6.1 Current architectural boundary

The scheduler is instantiated within a `SageTransport` instance. Its lane key is currently derived from:

```ts
request.companyId ?? config.companyId ?? "default"
```

This means coordination is local to one transport instance. Separate SDK clients and separate application processes do not share scheduler state.

### 6.2 Requirements

1. Document the scheduler's exact lifecycle and scope.
2. State clearly that per-company isolation applies only within one scheduler instance.
3. Explain that multiple clients using the same API key, user and company may collectively exceed a Sage-side quota even if each local scheduler is behaving correctly.
4. Explain that multiple application processes or replicas are not coordinated.
5. Do not claim deployment-wide or account-wide rate limiting.
6. Do not introduce Redis, a distributed lock, a broker dependency or other external coordination infrastructure in this work package.
7. Do not make the scheduler a process-global singleton as a shortcut; that would introduce hidden shared state and lifecycle ambiguity.
8. Consider whether an injectable scheduler instance is useful for applications that deliberately share one client-side coordination domain. Implement this only if it can be achieved without compromising ownership, shutdown semantics, isolation or public API simplicity.

### 6.3 Company identity

Review the lane key and verify that its identity is stable and unambiguous for the configured Sage company.

Do not log credentials or tokens as lane identifiers.

If the current company identifier is insufficient to distinguish the documented Sage rate-limit scope, record the limitation and propose a safe identity model. Do not include API secrets in keys, snapshots or logs.

### 6.4 Acceptance criteria

- [x] Scheduler instance scope is documented.
- [x] Multi-client and multi-process limitations are explicit.
- [x] No distributed coordination dependency is introduced.
- [x] Effective upstream throttling identity (API key, company and user) is reviewed against the SDK's actual authentication model and tested.
- [x] Snapshot and logging output contain no credentials or sensitive payloads.
- [x] Any injectable/shared scheduler proposal is either justified and implemented with tests or explicitly deferred.
